## 1. THE BLUETOOTH CALL-AUDIO ANSWER (phone-link)
phone-link does NOT get call audio on the Mac. Its README says so explicitly: "macOS gives apps no voice link to a phone over Bluetooth ... no mute, hold, keypad or moving a call to the Mac." Calls are controlled, audio stays on phone/headset.
Exactly how call CONTROL works (engine/crates/calling/src/control/{mod,at,link}.rs, bluetooth/src/{lib,edge}.rs, gui/PhoneLinkKit/Edges/PhoneBluetoothAdapter.swift):
- Bluetooth CLASSIC (not BLE, no MAP/PBAP/ANCS). Mac plays the HFP Hands-Free (HF) role. It opens an RFCOMM channel to the phone's HFP Audio Gateway SDP service (UUID 0000111F-0000-1000-8000-00805F9B34FB) using IOBluetooth: IOBluetoothDevice.pairedDevices(), IOBluetoothDeviceInquiry, IOBluetoothDevicePair, and RFCOMM opened from the SDP records macOS already holds for the paired phone (PhoneBluetoothAdapter.swift:48 rfcommOpen; refreshServices :69 re-reads SDP when the AG service is missing).
- Mac speaks raw HFP AT commands itself over that RFCOMM stream: AT+BRSF=0x66 (3-way, CLI, enhanced call status, enhanced call control; codec negotiation, voice recognition, remote volume deliberately omitted because they need SCO), AT+CMEE, AT+CIND=?/?, AT+CMER=3,0,0,1, AT+CHLD=?, AT+CLIP=1, AT+CCWA=1, then ATA (answer), AT+CHUP (reject/hangup), ATD<number>; (dial), AT+CLCC (call list), +CIEV/RING/+CLIP unsolicited (at.rs:144-170, mod.rs:734-752). No SCO/eSCO link is ever opened.
- Pairing: the Mac pairs with the phone by Bluetooth NAME (phone's Bluetooth name learned from the Microsoft Link-to-Windows app, which also makes the phone discoverable via a BluetoothAdvertise permission request). Numeric-comparison confirmation is shown in an alert and answered through a PRIVATE CoreBluetooth pairing agent via runtime selector call because IOBluetoothDevicePair.replyUserConfirmation is a no-op on current macOS (PhoneBluetoothAdapter.swift:234-260). Entitlement: just NSBluetoothAlwaysUsageDescription; no special entitlement.
- Incoming call ring on Mac is a system "Glass" sound loop (CallRinger.swift); the phone's ringtone cannot play on the Mac. Reconnect has no timer: retry on app foreground and on "phone connect complete" (mod.rs header).
- Limits: Android's HFP AG normally serves one HF at a time; a phone already connected to a car/headset HFP may refuse or drop one of them (not tested here, my inference). Needs Classic pairing (not just BLE). Call history comes from the Link-to-Windows channel, not Bluetooth.
Implications for DroidDock bt-calls:
 (a) DroidDock can get the same CONTROL-over-Bluetooth path with zero cloud: Mac = HF via IOBluetooth RFCOMM to 111F + AT commands (MIT code, adaptable with credit). Value: works with Wi-Fi down, no WS needed. But DroidDock already controls calls over Wi-Fi via the app; the new value is Wi-Fi-less control and a fallback.
 (b) It confirms audio on Mac is NOT achievable with the public path phone-link found. Untested lead worth a 1-2 h spike: IOBluetoothHandsFreeDevice and IOBluetoothSCOAudioDevice (older IOBluetooth HF/SCO classes) - phone-link authors did not use them and say audio is impossible; do not promise it. Realistic audio route stays: CALL_AUDIO_INTERCEPTION over adb (already proven) or a Wi-Fi audio stream from the phone app.
 (c) Tells us the Bluetooth-name matching + private CB pairing agent trick exists; if bt-calls does Classic pairing, copy the idea (clean-room from MIT code ok).

## 2. Architecture summary
phone-link: uses Microsoft "Link to Windows" (phone has MS app, Mac signs into MS account). Transport = SignalR cloud relay + Nano/ICE/SRTP direct (engine/crates/{transport,nano}). No own Android app. ToS/account-ban risk (README disclaimer), depends on Microsoft protocol; not a model for DroidDock's own-protocol design. Reusable ideas only in Mac-side UX/edges.
AirSync: own Android app + Swift Mac app (44.8k lines Swift, 33.7k Kotlin). Mac runs Swifter HTTP/WebSocket server ws:// plain on LAN; app-layer AES-256-GCM with a shared key from the QR (Core/Util/Crypto/CryptoUtil.swift). Discovery: Bonjour + UDP broadcast + phone-side wake-up HTTP :8888 / UDP :8889 (QuickConnectManager.swift). Mirroring/remote/call control/file browse use ADB + scrcpy (brew deps). Quick Share both ways (Core/QuickShare, own Swift impl).

## 4. Idea list
(Value H/M/L, Effort S/M/L; license; session)

1. BLE connect hangs (bt-offline). AirSync BLECentralManager.swift has the identical problem and the identical workaround ("connect() has no timeout... hangs forever with stale pairing data", 10 s watchdog, cancelPeripheralConnection, retry scan after 2-3 s; also scan restart every 10 s, prune stale after 15 s). DroidDock already does 10 s cancel (BleService.swift:362-378) so the ~10 s hang we see = the watchdog firing, i.e. connect() never completes. AirSync differences worth testing: (i) it advertises a CONSTANT service UUID connectable, ADVERTISE_MODE_BALANCED, TX medium, name only in scan response (BleGattServer.kt:189-231) and matches on UUID; DroidDock matches on a rotating service-data rid and says "address rotates". Test: connect to RPA fails if the Mac holds an old resolvable address; try connecting immediately in didDiscover with the fresh peripheral (already) but also retrievePeripherals/ scan filter on UUID only, and verify phone advertises connectable on API 31+ with setConnectable(true) and GATT server opened BEFORE advertising. (ii) AirSync authenticates only after ALL expected services are discovered (expectedServiceCount=4) and then writes token; separate handshake chars. (iii) it pauses phone advertising while Wi-Fi is up (pauseAdvertising) and drops BLE only after Wi-Fi is stable 5 s (wifiStabilityTimer) - avoid flapping. H, S-M, MPL: ideas only, session bt-offline. Also: add exponential backoff and a "BLE bonded/stale" reset, plus log CBError code on didFailToConnect.
2. Hands-free-profile control path without Wi-Fi (bt-calls). See section 1: Mac HF via IOBluetooth RFCOMM + AT commands gives answer/reject/hangup/dial/caller-number/call list with only Bluetooth Classic. H (fallback + works with Wi-Fi off), M-L effort (Classic pairing UX, one-HF conflicts), MIT adapt+credit. bt-calls.

## 5. Top takeaways
- Calls: no vendor has Mac call audio; phone-link proves control-only HFP. Don't chase audio via public Bluetooth APIs.
- Camera: system extension needs paid Developer ID; plan the team account first.
- BLE hang: AirSync has the same CoreBluetooth no-timeout behaviour; its recipes are constant UUID matching, 10 s watchdog + 2-3 s rescan, auth after full service discovery, Wi-Fi-stability gating.
- Distribution gaps for DroidDock: Homebrew cask, notarization, translocation check, Share extension.
