## A. Sefirah facts (read in code)
- Model: LAN only, Windows = TLS TCP server (ports 5150-5169, Sefirah/src/Sefirah/Services/NetworkService.cs), Android ALSO runs an SSLServerSocket and can connect either direction (Sefirah-Android core/network/.../NetworkService.kt L144,279,433-531). Discovery: UDP broadcast + NSD/mDNS + QR + "trusted networks" screen (TrustedNetworkScreen.kt). Auth: JSON `Authentication{deviceId,publicKey}` verified against the TLS peer cert (SslHelper.verifySessionCertificate); 10 s auth timeout inbound, 3 s outbound. Messages = JSON sealed class w/ "type" discriminator (domain/.../SocketMessage.kt). No cloud path.
- Calls: phone sends CallInfo (ringing/missed/in-progress + contact) -> toast. Real call audio on Windows = Windows' own PhoneLineTransportDevice over classic Bluetooth HFP (Platforms/Windows/Calling/PhoneLineService.cs, uses an unlock hack TryUnlockPhoneLineTransportDeviceAPIs). Phone side only has BluetoothPairingHandler + BluetoothDiscoverableActivity; protocol messages BluetoothPairingRequest/Result drive pairing over the LAN link. Desktop (Linux/mac) BluetoothPairingService is a stub (IsBluetoothSupported=>false). => No Bluetooth transport for data; BT is audio-only, and only works because Windows has an OS HFP-client API. macOS has none => confirms DroidDock's bt-calls block.
- SMS: incremental sync by per-thread checksum (SMSHelper.kt L483-602: checksum=17, *31 rolling over rows; desktop sends KnownThreads[{id,checksum}] and phone returns only changed threads; Sefirah/.../Features/SmsFeature.cs L31-47) + offline outbound queue flushed on reconnect.
- Notifications: RECEIVE_SENSITIVE_NOTIFICATIONS appop (Android 15 hides OTPs/sensitive notifs) granted automatically via ADB when device online (README). Clipboard on 10+: a11y service + Shizuku or desktop-ADB.
- Mirror: spawns scrcpy with many per-device args, incl --turn-screen-off, --keyboard=uhid, --start-app, --video-buffer (Services/ScreenMirrorService.cs).
- Valent (GNOME KDE Connect, src/plugins/lan/valent-lan-channel-service.c): handshake timeout constant (1 s, 10 s in debug), identity packet marked with intended target so broadcast responders can abort; ignores own broadcasts; dual v4/v6 UDP sockets. Plugins are isolated Peas extensions per device (src/plugins/*) so one plugin failing cannot hang the channel. Minor value.

## B. Phone camera -> Mac webcam
Current DroidDock: scrcpy `--video-source=camera --camera-facing=back` in its own window (droiddock-native/core/src/adb.rs L1253-1257). No virtual camera, nothing selectable in Zoom/Meet.

Real requirements for a CMIOExtension virtual camera (verified: iPhone2MacVirtualWebcam entitlements/Info.plist, liveloop DESIGN.md, Apple forum threads 736838/710046):
1. System extension bundle (.systemextension in app/Contents/Library/SystemExtensions) with Info.plist `CMIOExtension{CMIOExtensionMachServiceName = <AppGroupPrefix>.something}`; mach service name MUST be prefixed by an app-group that is in both signatures' entitlements.
2. Host app calls OSSystemExtensionManager (VirtualCameraInstaller.swift); app must be in /Applications.
3. Host app needs RESTRICTED entitlement com.apple.developer.system-extension.install, authorized by a provisioning profile with System Extension capability. Free/personal teams cannot get it. Self-signed / ad-hoc => sysextensiond says "Extension not found in App bundle" even with SIP off.
4. Distribution: Developer ID Application + secure timestamp + notarization, separate Developer ID profiles for app AND extension; activates with SIP on. Dev path: dev profile + `systemextensionsctl developer on` (needs SIP off) allows un-notarized.
5. Legacy DAL plug-ins (no entitlement needed) are not loaded by modern Zoom/Meet/Teams (hardened runtime, library validation) => not a workaround.
=> A SwiftPM-only, self-signed, un-notarized DroidDock CANNOT ship a native virtual camera. Needs paid Apple Developer ($99/yr), Xcode-or-xcodebuild signing with profiles (SwiftPM can build the binary, but the .systemextension bundle + embedded.provisionprofile can be hand-assembled by a script and signed with `codesign`; Xcode not strictly required, but the profile must be downloaded from the Apple developer portal).

Architecture to copy (idea; Cam2Camera, VirtualCameraExtensionProvider.swift 493 lines):
- Two CMIO streams: a SINK stream (host app writes decoded CVPixelBuffers via CMIOStreamCopyBufferQueue/ sink client, sinkBufferQueueSize=4, sinkBuffersRequiredForStartup=1) and a SOURCE stream apps read. Extension only forwards; all network/decode stays in the host app (keeps extension tiny and sandbox-safe).
- Jitter buffer in extension: max 3 pending frames, output on a strict 30 fps DispatchSourceTimer, re-stamp PTS with host clock (CMSampleBufferCreateCopyWithNewTiming), drop 1 frame if backlog persists ~1 s so latency doesn't grow; sink consume loop polls at 4 ms when empty; generation counter so only one consume loop lives.
- Fixed 1280x720 32BGRA 30 fps device ("Remote Camera"). Transport: H.264 Baseline AutoLevel, RealTime, no B-frames (H264Encoder.swift L170-191) over QUIC w/ pinned cert; decode VideoToolbox. Optional Metal background-blur in host app.
DroidCam (GPL-2): OBS plugin pulls MJPEG (libjpeg-turbo, tjDecompress) or H.264 via ffmpeg from phone over TCP/USB(adb/usbmuxd) and relies on OBS's own notarized virtual camera. StreamBerry-Cam: same OBS approach, claims 50-150 ms WebSocket, 200-500 ms MJPEG (unverified marketing).
